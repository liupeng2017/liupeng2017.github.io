Pixso（最新项目产品）

最新的项目产品是 Pixso，一款在线协作的 UI 设计与交付工具，覆盖从画布绘制、设计规范到研发交接的完整链路。下面按组件、组件库、变量、文本、布局、渲染六个重点各配一张官方站点截图说明。

组件

组件把可复用的界面单元（按钮、头像、导航栏等）做成母版，页面里放的是它的实例。颜色与按下、松开等状态共同组成组件变体，实例通过属性面板选择对应组合，不用为每个状态单独画一份。

尺寸为不同场景、内容为长标题或不同按钮文案，都可以用变体组织尺寸与状态，再用文本、图层可见性和实例交换属性控制内容；配合自动布局，按钮会随文案长短自动伸缩，列表会随条目增减自动重排。为默认、悬停、禁用、加载、错误和成功状态建立变体，是组件在真实产品里的主要用法。

组件库

样式用于复用成组的视觉属性——颜色、文本、效果和布局网格集中管理，改一次定义，所有引用它的图层同步更新。基础样式与可复用组件在同一份设计文件中维护。

组件和样式可以发布为团队资源库，其他设计文件启用后即可复用，更新由团队有序接收——不是静默覆盖，而是接收方按需同步，避免正在改的稿子被突然刷新。

变量

变量用来管理可重复使用的值：用颜色、数值、文本和布尔变量组织属性值，把尺寸、间距、圆角或主题变化落实到图层。数值变量一套就能驱动间距和圆角，布尔变量控制显隐与开关态，文本变量切换多语言文案，颜色变量挂上主题模式后浅色、深色一键切换。

文本

文本样式把字号、行高、字重成组复用，保证标题、正文、辅助说明在各页面保持一致。团队可以统一字体和字重，减少换设备后出现的排版差异。

可变字体在一个字体文件里连续调节字重，从细体到加粗不再依赖多个字重文件，排版更细腻，也更容易和变量、文本样式配合做统一的文字规范。

布局

自动布局让内容决定排列：设置方向、间距、内边距与尺寸规则后，容器随内容增减自动扩展，条目按规则对齐，不必手动挪像素。做响应式卡片、工具条、列表时最省事。

布局网格也可以作为样式复用，把列数、间距、边距定成规范，多个页面共享同一套栅格。

渲染

设计稿进入研发阶段后靠渲染输出：交付模式里查看所选图层的属性、间距标注与盒模型，并拿到参考的样式代码，实现可以直接照抄数值。

资源按需批量导出 PNG、SVG 等格式与倍率，背景与切图设置都在属性面板里完成，一次配置输出多个尺寸。设计稿中的布局、样式与资源可以转换为前端实现的起点，减少来回截图、猜间距的沟通成本。

WinPE 启动盘制作 + Windows 11 专业版安装全流程

2026-11-09

适用场景：新装机、系统崩溃进不了桌面、或者想彻底重装一块系统盘。整篇流程走下来大概半小时。文中 clean 一步会清空整块磁盘，操作前务必备份数据，无价。

一、准备工作

三样东西：

  • 一个 8GB 以上的 U 盘。制作启动盘会格式化它，里面原有的东西先拷出来。
  • PE 制作工具。推荐微 PE 工具箱，从官网下载：https://www.wepe.com.cn/。其他惯用的 PE 工具也可以，但一定走官方渠道——下载站的安装包经常捆绑全家桶，PE 环境被植入东西比系统中毒还麻烦。
  • Windows 11 专业版 ISO。到微软官方下载页：https://www.microsoft.com/zh-cn/software-download/windows11，选择简体中文 64 位镜像。网上流传的 ISO 直链大多带时效签名，过几个小时就失效，所以本文只放官方页面。下载完建议用页面给出的哈希值校验一下完整性。

顺带一提：如果只是想给一台还能正常开机的电脑干净重装，用微软官方的 Media Creation Tool 或 Rufus 直接写 ISO 更省事；PE 的价值在于磁盘分区、引导修复这些维护操作，以及系统已经起不来时的兜底。

二、制作 PE 启动盘
  1. 解压下载好的 PE 工具，双击其中的「U盘启动制作工具」。
  2. 设备选择你的 U 盘，镜像选择 PE 的 ISO。
  3. 点击开始制作，等进度走完。再强调一次：这一步会清空 U 盘。
三、从 U 盘启动

插上 U 盘，开机时不停按启动菜单快捷键，在菜单里选择带 UEFI 前缀的 U 盘启动项（不要选 Legacy 项，后面要用 GPT + UEFI 引导）。

常见品牌的启动菜单键：

品牌 快捷键
联想 / 戴尔 / 华为 / 宏碁 F12
华硕 F8
微星 F11
技嘉 F12
惠普 Esc

以开机画面下方的提示为准，手速要快，现在 NVMe 机器开机很快，错过就得重来。

四、建立 GPT 分区引导

进入 PE 桌面后，先打开控制台（命令提示符），用 diskpart 把目标磁盘转成 GPT：

逐行解释：

  • list disk 列出所有磁盘，按容量确认目标盘的编号，下一步的 0 要换成实际编号。选错盘就是把别人的数据清掉了。
  • clean 清空该磁盘的全部分区和数据，不可逆。
  • convert gpt 转换为 GPT 分区表，这是 UEFI 引导的前提。

然后打开 PE 里的磁盘分区工具（DiskGenius 之类），用「快速分区」：

  • 分区表类型选 GUID（GPT），工具会自动创建 ESP 引导分区和 MSR 保留分区，这两个别删；
  • 系统盘 C 盘建议分 100GB 以上；
  • 勾选 4K 对齐（SSD 必须）。
五、还原系统

打开 PE 里的「系统还原工具」（CGI、Dism++ 这类都可以）：

  1. 映像文件选择下载好的 Windows 11 ISO，工具会读取其中的 install.wim，版本选专业版；
  2. 目标分区选刚分好的 C 盘；
  3. 勾选「修复引导 / 添加引导」，引导分区指向那个 ESP 分区；
  4. 开始还原，等进度条走完。
六、重启，完成安装

还原完成后重启，第一时间拔掉 U 盘，让机器从硬盘启动。之后 Windows 会自动完成设备部署并进入开箱设置（OOBE），按提示配好区域、键盘、账户就能进桌面了。

先看清整条链路

很多人把「Hexo 部署」当成一条命令，出问题时才发现它其实是四段独立的东西，每一段都会单独坏掉。

挂自己的域名

域名解析这一层和 Hexo 完全无关，但最容易在这里翻车。

CNAME 文件由谁生成。 Pages 靠仓库根目录的 CNAME 记住你的域名。而 hexo-deployer-git 的机制是：清空 .deploy_git → 把 public/ 整个复制进去 → git add -A → git push --force。也就是说线上分支的内容严格等于 public/，你手动提交到那个分支的 CNAME（或者任何文件）会在下一次部署时消失，force push 也不给你在线上分支直接改内容的余地。装了 hexo-generator-cname 之后，它每次 hexo generate 都把 _config.yml 里 url 的域名写进 public/CNAME，产物带着它走，就不会丢。我没在 source/ 下手写过 CNAME，一个插件解决的事不需要两份真相。

DNS 怎么填。 顶级域（example.com）不能用 CNAME（RFC 限制，CNAME 不能与其他记录共存），要填 GitHub Pages 的四台 A 记录；www 用 CNAME 指向 <用户名>.github.io。四个 IP 以 GitHub 官方文档当期给出的为准，别抄博客里的旧值：

主机记录 类型 值

www CNAME <用户名>.github.io

我在这个站上真实踩过的坑

按「值得别人也防一遍」排序：

  1. 主题模板里的相对路径。 yilia 的 layout.ejs 有一行 src="../source-src/js/clicklove.js"。这个文件确实躺在主题的 source-src/ 里，但构建不会把它复制进站点产物，所以首页把它解析成 /source-src/...、文章页解析成 /年/月/日/source-src/...，两种都验证过是 404——也就是说「点击出现小红心」这个功能一直是坏的，直到为写这篇去翻 Network 面板才发现。教训：模板里引用资源一律用 url_for()，并且别假设「源码里有这个文件」等于「线上能取到」。
  2. 配置里留了个没人实现的入口。 _config.yml 写着 rss: /atom.xml，但没装 hexo-generator-feed，于是 /atom.xml 一直 404，主题侧边栏的 RSS 图标是个死链。要么补插件，要么把这个入口关掉——留个坏掉的图标比没有更糟。favicon.png 也是同一类问题。
  3. 模板报错会被静默吞掉，产出 0 字节页面。 我新写聚合页时用了 partial('post/title')，实际路径应该是 partial('_partial/post/title')。hexo generate 的 exit code 正常、日志看不出问题，只有产物大小是 0。所以构建之后要有一步「抽查关键页面的字节数和标题」，而不是只看命令有没有报错。
  4. 图床防盗链。 从第三方内容平台搬运过来的文章，图片指向对方 CDN，直接外链在自己的域名上会被防盗链拦掉。做法是把附件全部下载到本地 images/<来源平台>/<文章ID>/ 并重写链接，这一步要独立的同步脚本，别指望 Markdown 渲染帮你做。
  5. .deploy_git 不是工作区。 想改线上内容去 source/ 改，在那儿改的东西下次部署就没了。

还有两个我没验证完、但建议你上线前检查的点：一是 hexo-generator-json-content 生成的 content.json 会不会把加密文章的正文带出去（我还没逐项核对，如果带出去就得给私密文章加排除）；二是加密文章的标题、摘要仍会出现在归档页和 sitemap 里——这是这类插件的固有行为，接受不了就得换部署方式（比如私密内容不放静态站）。

一、后台任务、线程、Worker、Native 子进程
  1. 需要在后台运行的耗时任务只在所有线程都空闲时才触发执行。
    判断：正确。taskpool 的 IDLE 优先级就是给后台耗时任务用的，只在空闲时执行。原题还有半句「同一时间仅有一个同 IDLE 优先级任务执行」，这半句我在官方文档里没找到原句，按前半句判断即可。
  2. Worker 线程支持同步调用主线程接口。
    判断：错误。Worker 与主线程通过 postMessage 异步通信，不支持同步调用。
  3. entry 模块中引入 HAR 包内的 Worker 对象，路径写成 har/ets/workers/Worker.ets。
    判断：正确。跨包引用 Worker 时要带上模块名。
  4. NativeChildProcess_MainProc 返回后子进程不会自动退出，需要手动调用终止接口。
    判断：错误。MainProc 返回后子进程自动退出。
  5. 回调 onProcessStart 在主线程运行，不需要考虑线程同步。
    判断：错误。回调运行在子进程自己的线程里，跨进程交互必须考虑同步。
  6. NativeChildProcess_OnConnect 的执行优先于 NativeChildProcess_MainProc。
    判断：原题判正确（存疑）。OnConnect 是客户端发起连接时的 IPC 回调，常规实现里 MainProc 反而更早，先后顺序请以当期 NativeChildProcess 文档和示例为准。
  7. 应用退到后台申请长时间任务，同一 UIAbility 同一时刻最多支持两个长时任务（API 20 及之前）。
    判断：错误。API 20 及之前一个 UIAbility 同一时刻最多持有 1 个长时任务，API 21 才放宽到最多 10 个。
  8. 主线程与其他线程存在大量数据交互时，可以用 @Unsafe 装饰器做线程间传递与同步。
    判断：错误。并发 Actor 模型用的是 @Sendable，没有 @Unsafe 这个装饰器。
  9. Actor 并发模型支持传输 Serializable 对象。
    判断：错误。Actor 消息传递支持 Sendable、Transferable；Serializable 是持久化用的，不能作为 Actor 传参。

  4. 被 @Trace 装饰的属性变化时，只会通知与该属性关联的组件刷新。
    判断：正确。这就是 V2 的精准更新，按属性粒度刷新依赖节点。
  5. 未被 @Trace 装饰的属性变化也能触发 UI 刷新。
    判断：错误。V2 只有 @Trace 标记的属性变更才驱动 UI。
  6. V2 的双向绑定用 !! 语法糖，自定义组件的双向绑定通过 @Param + @Event 组合实现。
    判断：正确。
  7. @Provide / @Consume 摆脱逐层传参，可以跨层级传递数据。
    判断：正确。
  8. @Provide / @Consume 能实现祖先与后代组件的双向数据同步。
    判断：正确。两者是同一份状态的双向绑定。
  9. @Provide / @Consume 可以在多层级父子组件之间传递状态。

    判断：错误。数量不改变结论，深层属性照样不触发刷新。

    判断：原题判正确（存疑）。预览器的能力边界随 DevEco Studio 版本变化，以当期文档为准。

    判断：原题判正确（存疑）。与第 23 题同一组限制。

    判断：错误。@Link 依赖父组件传入的绑定，单独预览会初始化失败，要预览父组件。

    判断：错误。@Consume 依赖祖先的 @Provide，单独预览取不到状态。

  6. DevEco 本地模拟器用于在个人电脑上模拟鸿蒙环境，方便应用与服务调试。
    判断：正确。
  7. macOS 运行 DevEco 本地模拟器，系统版本至少 12.5。

    判断：错误。官方不支持虚拟机嵌套运行模拟器。
  9. Mac 运行本地模拟器推荐至少 8G 内存。
    判断：原题判正确（存疑）。同第 29 题，以官方配置要求为准。

五、UIAbility、Want、任务栈、生命周期、HAR / HSP / HAP

一、ArkTS 与 TypeScript 的差异（禁用清单）

ArkTS 为了编译期能确定对象布局、便于 AOT，砍掉了 TypeScript 里一大票动态特性。这一节几乎每年必考，判断题直接命中。

替代方案记住四个词：明确类型、联合类型、泛型、Map。类型兼容要用名义类型，即显式 implements / extends，光长得一样不算。

二、@State / @Prop / @Link
装饰器 数据源 方向 一句话
@State 组件自身 自身 ↔ UI 私有状态，只观察第一层
@Prop 父组件 父 → 子单向 子组件改了不回传，对象是深拷贝
@Link 父组件 父 ↔ 子双向 父用 $ 传引用，子不能本地初始化

延伸三个：跨层级用 @Provide + @Consume（双向）；观察嵌套对象用 @Observed + @ObjectLink；变化监听 V1 用 @Watch、V2 用 @Monitor。

Storage 一族按作用域记：AppStorage 是应用级内存，PersistentStorage 是应用级持久化，LocalStorage 是页面级。带 Link 的双向，带 Prop 的单向。

三、状态管理 V1 → V2 对照
V1 V2
@Component @ComponentV2
@State @Local
@Prop @Param（配 @Once）
@Link @Param + @Event
@Provide / @Consume @Provider / @Consumer
@Observed + @ObjectLink @ObservedV2 + @Trace
@Watch @Monitor
— @Computed（有缓存，依赖变了才重算）

硬规则：V1 和 V2 不混用。@Param 是只读的，想改就得通过 @Event 回调父组件，这是 V2 的单向数据流。

四、TaskPool 与 Worker
对比 TaskPool Worker
级别 任务级 线程级
线程管理 自动 手动
适合 短时、独立、CPU 密集 长时、常驻、频繁通信
装饰器 @Concurrent —
通信 参数 / 返回值 postMessage / onmessage
数量 由任务池调度，优先级 HIGH/MEDIUM/LOW API 12+ 最多 64 个，旧版 8 个

两者共同点：都是 Actor 模型，内存隔离，都不能更新 UI（UI 只在主线程改）。

@Concurrent 修饰的函数四条限制：不能用闭包变量、不能用 this、不能操作 UI、参数和返回值要可序列化。跨线程共享对象用 @Sendable，普通对象默认是序列化拷贝，不是共享引用。
